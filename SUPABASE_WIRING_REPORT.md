# Supabase Wiring Report

## Summary

Tetisol Hub was still demo-first before this fix. The main app provider loaded `localStorage` and `defaultCareerHubState` before checking Supabase, so the live Netlify app could show courses, learner personas, progress, CV data, and opportunities even when the official database was missing or empty.

The app is now production-first:

- Production mode uses Supabase-backed state only.
- Local/demo seeded state is available only when `NEXT_PUBLIC_ENABLE_DEMO_MODE=true` in development.
- Auth uses Supabase Auth when Supabase env variables are present.
- Course, lesson, opportunity, enrollment, progress, saved opportunity, CV, and profile flows now call Supabase service functions.

## Demo Data Found

Demo/local data was found in:

- `lib/demo-data.ts`: seeded courses, internships, personas, learner workspaces, certificates, CVs, and progress.
- `services/storage.ts`: browser `localStorage` persistence.
- `services/career-hub-service.ts`: local sign-in/sign-up and state mutation helpers.
- `components/providers/career-hub-provider.tsx`: initialized the UI from local/demo state and persisted to `localStorage`.
- `components/auth/auth-panel.tsx`: displayed demo personas and demo login instructions.
- `app/(app)/internships/[slug]/page.tsx`: statically generated internship routes from demo data.

## What Was Replaced With Supabase

New/updated Supabase-backed pieces:

- `services/supabase-state-service.ts`
  - Loads published courses and lessons from `courses` and `lessons`.
  - Loads opportunities from `opportunities`.
  - Loads current profile from `profiles`.
  - Loads enrollments from `enrollments`.
  - Loads progress from `lesson_progress`.
  - Loads saved opportunities from `saved_opportunities`.
  - Loads CV data from `cv_profiles`.
  - Writes enrollments, progress, saved opportunities, profile updates, and CV updates back to Supabase.
- `components/providers/career-hub-provider.tsx`
  - Uses remote Supabase state by default.
  - Refreshes state on Supabase auth changes.
  - Stops saving production state to `localStorage`.
- `components/auth/auth-panel.tsx`
  - Removed seeded persona cards and fake credential instructions.
  - Uses Supabase sign-in/sign-up flow.
- `app/debug/backend/page.tsx`
  - Adds backend health checks for env detection, auth user, profile row, courses count, opportunities count, and enrollments count.

## Remaining Local/Fallback Behavior

The code still contains demo data for explicitly enabled local development mode only:

```text
NEXT_PUBLIC_ENABLE_DEMO_MODE=true
```

This mode is disabled by default in `.env.example` and must not be enabled on Netlify.

Some secondary features still remain local UI state until the next database pass:

- Learning notes
- Quiz attempts from the legacy local quiz system
- Certificates generated by local progress logic
- Application tracker records
- Admin content editor persistence to Supabase

These do not block the core 50-user Supabase proof for auth, courses, lessons, enrollments, progress, opportunities, saved opportunities, profiles, and CV data.

## Supabase Connectivity Verification

A direct public-key check reached the official Supabase project, but the required tables were not present:

```text
Could not find the table 'public.courses' in the schema cache
Could not find the table 'public.opportunities' in the schema cache
Could not find the table 'public.profiles' in the schema cache
```

Conclusion: the app is wired to query Supabase, but the official Supabase project still needs the schema and seed data applied.

## Remaining Limitations

- The official Supabase database is not ready until `supabase/schema.sql` is run in the Supabase SQL editor.
- Seed data cannot be pushed without `SUPABASE_SERVICE_ROLE_KEY` in local `.env.local`.
- Existing Netlify deployment will not change until these commits are pushed and Netlify redeploys with the required env vars.
- Admin content editing still updates local UI state first; database persistence for admin CMS edits should be the next hardening pass.
